# Nitro Input

`react-native-nitro-input` is the second package in this repository, and it ships two
components over one native field:

- **`NitroInput`** — a plain native input. The system field draws its own text, so it
  costs no more to mount than a bare `UITextField` / `EditText`. This is the one you
  reach for by default.
- **`MorphInput`** — the same field with the morph on, for the screens where the
  animation is the point (in practice, amounts).

`MorphInput` morphs its text the way [Torph](https://torph.lochie.me) morphs text on the web. Characters that stay glide to their new place, new ones slide or fade in, removed ones leave alongside their neighbours. A comma that reflows travels to where it now belongs instead of blinking into existence.

It is a real input. A system text field (`UITextField` on iOS, `EditText` on Android) owns the keyboard, editing, selection, paste and accessibility; the morph layer on top only draws its glyphs. What makes it different from a `TextInput` that formats in `onChangeText`:

- **Formatting happens natively, before a frame is drawn.** In `mode="number"` every keystroke goes through the same C++ formatter on both platforms: grouping separators, one decimal separator, at most `fractionDigits` decimals, the caret kept where you typed, a digit too many rejected outright. The JS thread only learns about the result, so there is no flicker, no caret jump and no dropped keystroke, however busy React is.
- **The same formatting model as the rolling number**: `prefix` / `suffix` at their own sizes, pinned to the top, bottom, baseline or centre of the digits; grouping and decimal separators of your choice.
- **One engine.** The matching (which characters persist, enter and leave), the slide, fade and scale curves and the timing live in `cpp/MorphEngine.cpp`, shared by Swift and Kotlin.

bun add react-native-nitro-input react-native-nitro-modules

## An amount field

<Example
  code={`import { MorphInput } from 'react-native-nitro-input'

const [amount, setAmount] = useState(NaN)

<MorphInput
  mode="number"
  prefix="$"
  prefixFontSize={28}
  affixAlign="top"
  placeholder="0"
  fractionDigits={2}
  fontSize={48}
  fontWeight="700"
  textAlign="center"
  style={{ width: '100%' }}
  onChangeValue={setAmount}          // 1234.5, or NaN while empty
/>`}>
  <NitroInputAmountDemo />
</Example>

Type `1234` and the field shows `$1,234`: the `1` slides over to make room as the comma arrives from below, the `4` drops in from above. Type `.5` and the decimal point and the `5` follow. Backspace over the comma and it takes the digit before it with it.

Keep the field uncontrolled and read `onChangeValue` (the number) or `onChangeText` (the formatted string), or pass `value` to drive it. A `value` that merely echoes `onChangeText` back never fights the user, native already shows it; a `value` that differs (a "Max" button, a clamp) is applied and morphs in.

## Worklets

With `react-native-worklets` installed (it ships with Reanimated 4), a `transform` worklet and worklet-marked `onChangeText` / `onChangeValue` handlers run on the UI thread *inside* the native edit, before a frame is drawn: a mask written in JS applies with no flicker, and a shared value is updated with no JS thread in between. This is the mechanism of Expo UI's worklet callbacks and react-native-transformer-text-input, with the native formatter still running first in `mode="number"`.

```tsx
const usernameTransform: NitroInputTransform = ({ text }) => {
  'worklet'
  const cleaned = text.replace(/[^0-9a-zA-Z_]/g, '').toLowerCase()
  return { text: cleaned ? '@' + cleaned : '' }
}

<MorphInput placeholder="@username" transform={usernameTransform} />

const progress = useSharedValue(0)
<MorphInput mode="number" onChangeValue={(value) => { 'worklet'; progress.value = value / 10 }} />
```

Without `react-native-worklets` the props are ignored with a single warning and everything else keeps working.

## How the morph decides what moves

- **Typing** (a caret is known): everything before the caret pairs by position from the left, everything after it from the right, so the edit is exactly the characters that entered or left. Grouping separators are kept out of that walk, because a comma reflows with the magnitude rather than with the keystroke; they pair from the units end instead, so the thousands comma stays the thousands comma and glides. Unless the integer gained or lost a column — then every comma belongs a group further along, past the digits that just carried the other way, so it drops out and a new one rises rather than sliding through them. Typing in the fraction leaves the integer columns alone, and the commas simply glide.
- **A value set from code** (`setValue`, `setText`, `clear`, the `value` prop): digits pair by their column from the decimal point, so `1,204 → 1,318` swaps the three low columns in place. When the integer part gained or lost columns the digits pair by subsequence from the units end and the separators leave. Plain text pairs by longest common subsequence (`Continue → Confirm` keeps `Con`).

A character that persists eases to its new x. A new digit drops in from above (a separator rises from below) through the clipped line box, fading in over the first quarter of the morph; a leaving digit drops out the same way. Text characters fade and scale (0.95×). Characters that enter or leave ride along with their nearest persisting neighbour, so a word that grows or shrinks stays one shape. Reduce Motion snaps.

A placeholder is not a value — it is what the field shows *instead* of one — so
trading it for a value is a change of state rather than a morph, and it snaps.
The zero standing in for an empty field does not roll into the digit that lands
on it, and it is drawn in `placeholderTextColor`, which keeps its own
transparency. Going the other way the value still leaves as it would normally,
and the placeholder fades in where it belongs rather than dropping from above.

Six or more adjacent characters replaced with nothing surviving between them stop being characters that moved. There is no neighbour left to travel against, and sliding each one only smears the run, so it recedes as one shape instead: no slide, and a scale to 0.8× about the run's own centre rather than each character's. The arriving run comes forward out of that same centre. This is what a three-column jump looks like — `100,000 → 100,000,000` swaps one quantity for another rather than dropping seven characters through the line box, and the commas recede with the block instead of falling like digits.

## Props

The full table is in the package [README](https://github.com/ronickg/react-native-nitro-rolling-number/tree/main/packages/react-native-nitro-input#props). The ones you will reach for first:

| Prop | Default | |
| --- | --- | --- |
| `mode` | `'text'` | `'number'` formats as you type. |
| `fractionDigits`, `maxIntegerDigits` | `2`, `15` | Limits; digits past them are rejected. |
| `groupingSeparator`, `decimalSeparator` | `','`, `'.'` | |
| `prefix`, `suffix`, `affixAlign` | `''`, `''`, `'baseline'` | As on the rolling number. |
| `placeholder` | `''` | Swapped for the first character, not morphed into it — see below. |
| `duration`, `easing`, `effect` | `400`, `'expo'`, `'auto'` | The morph. |
| `keyboardType`, `returnKeyType`, `autoCapitalize`, `autoCorrect`, `maxLength`, `editable`, `autoFocus` | | Input traits. |
| `transform` | | A worklet mask, run synchronously on the UI thread. |
| `onChangeText`, `onChangeValue`, `onFocus`, `onBlur`, `onSubmitEditing` | | The change handlers may be worklets. |
| `submitBehavior` | `'blurAndSubmit'` | `'submit'` keeps focus so a form can move to the next field itself. |
| `secureTextEntry` | `false` | Draws bullets; the field keeps the real text for autofill. |
| `textContentType` / `autoComplete` | `''` | Autofill: `'username'`, `'password'`, `'oneTimeCode'`, … |
| `keyboardAppearance`, `enablesReturnKeyAutomatically`, `showSoftInputOnFocus` | | Keyboard behaviour. |
| `selectTextOnFocus`, `clearTextOnFocus`, `contextMenuHidden`, `spellCheck`, `readOnly` | | As on `TextInput`. |
| `selection` | | `{ start, end? }` in code points, controlled. |
| `onEndEditing`, `onSelectionChange`, `onKeyPress` | | The rest of `TextInput`'s edit callbacks. |

Imperative handle: `focus()`, `blur()`, `clear()`, `setText()`, `setValue()`, `getText()`, `getValue()`, `isFocused()`.

## A plain field

`NitroInput` is the same component without the morph: the system field draws
its own text, so there is no glyph engine, no per-glyph layers and no custom
caret. Everything else is identical — `'number'` formatting, the focus path,
React Native's text-input registry and keyboard-controller support.

```tsx
import { NitroInput } from 'react-native-nitro-input'

<NitroInput
  placeholder="Email"
  keyboardType="email-address"
  textContentType="username"
  style={{ height: 52, width: '100%' }}
/>
```

It takes every `MorphInput` prop except the morph ones (`duration`, `easing`,
`bounce`, `effect`).

## Benchmarks

Release builds; mount is 20 fields rendered in one state update, measured to
the last `onLayout` over 5 cold passes; focus is `focus()` → `onFocus` over 12
runs. Medians.

| target | mount: MorphInput | mount: TextInput | focus: MorphInput | focus: TextInput |
| --- | --- | --- | --- | --- |
| iPhone 13 Pro Max | 12.6 ms | **9.7 ms** | **4.5 ms** | 53.7 ms |
| iPhone 17 Pro simulator | 17.2 ms | **8.8 ms** | **4.1 ms** | 29.3 ms |
| Pixel 9 Pro emulator | **24.8 ms** | 62.6 ms | **2.0 ms** | 18.4 ms |
| Pixel 10 | **30.3 ms** | 41.7 ms | **2.5 ms** | 21.9 ms |
| Galaxy A22 (slow device) | **76.4 ms** | 90.8 ms | **14.1 ms** | 24.8 ms |

On the iPhone, `NitroInput` mounts in 12.9 ms and focuses in 10.6 ms — the same
mount as `MorphInput`, because the overlay is not what mount costs.

For a third point of reference, `@expo/ui`'s SwiftUI `TextField` on the same
device mounts 20 fields in **91.4 ms** and focuses in **107.4 ms** — roughly 7x
our mount and 24x `MorphInput`'s focus, and it is invisible to
`react-native-keyboard-controller`.

**Programmatic focus is faster**, because `focus()` is a direct call into the
hybrid that lands on the next runloop turn, and `onFocus` comes back from the
field's own delegate. `TextInput.focus()` goes through `TextInputState` and a
Fabric view command applied with the mounting transaction, then returns through
the batched event emitter — about a frame's wait either side. Tapping a field
is unaffected: the OS grants first responder directly, with no JS in the loop.

**The ratio depends on the device.** On fast hardware it looks like 8–9×; on a
budget phone it is 1.8×, because MorphInput's round trip costs real CPU while
`TextInput`'s frame wait stays roughly constant. The dependable claim is
**~10 ms saved per programmatic focus on a slow device**, more on a fast one.

**Mount** is cheaper than `TextInput` on every Android target measured, and on
iOS costs about 0.16 ms more per field. That difference is not this component:
a *different* Nitro view (`RollingNumber`, no text input, fewer props) mounts at
the same 12.2 ms per 20 that `MorphInput` and `NitroInput` do, against 9.1 ms
for `TextInput` and 4.1 ms for a bare `View`. It is the per-view floor of a
Nitro `HybridView`, roughly 0.6 ms each — measured on an iPhone 13 Pro Max over
15 cold passes.

Both components deliver `onFocus` **asynchronously**; the benchmark screen
checks that rather than assuming it, so the two numbers measure the same event.
Re-run any of this from the example app's **Mount / focus benchmark** screen.

## Working with the rest of React Native

`MorphInput` registers itself in React Native's text-input registry and answers
the `focus` / `blur` view commands, so the things that act on "the focused
input" work on it as they do on `TextInput`:

- `Keyboard.dismiss()`, `TextInput.State.currentlyFocusedInput()` and
  `TextInput.State.blurTextInput()`
- a `ScrollView`'s `keyboardShouldPersistTaps` / auto-blur
- `react-native-keyboard-controller`: the focused-input observer sees it,
  `KeyboardAwareScrollView` scrolls it into view, and `KeyboardToolbar`'s
  next/previous traverses into and out of it

`testID` and `accessibilityLabel` are forwarded to the hidden system field —
the element VoiceOver, TalkBack and e2e tools actually interact with — and the
`placeholder` is exposed as its accessibility value while the field is empty.

:::note Layout
Unlike `TextInput`, `MorphInput` sizes itself to its content. Give it a
`width` (or `flex`) in `style` to make it fill its parent the way a `TextInput`
does; without one it hugs the text and grows as you type.
:::
