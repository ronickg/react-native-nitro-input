# Benchmarks

Measured on three phones: an **iPhone 13 Pro Max** (120 Hz), an **iPhone 11 Pro** (60 Hz) and a **Samsung Galaxy A22** (90 Hz, a low-end MediaTek phone). Release builds, React Native 0.87.1. The bench app in the repository (`bench/`) is launched with a plan by `scripts/bench/run.mjs` and measures every frame on both threads with a native probe. Hover a bar for every figure of its row. The full tables, the method and the memory measurements are in [BENCHMARKS.md](https://github.com/ronickg/react-native-nitro-input/blob/main/BENCHMARKS.md), and every number comes from a result file in `scripts/bench/results/`.

## NitroNumber

**24 numbers, a new value every frame.** UI is the main thread's frame rate and the frames it missed; JS is the frame rate the JS thread still managed. Only paths whose per-update work is one call (Nitro `jumpTo`, AnimateableText) or a plain render (Text, the Nitro `value` prop) hold the display's rate on every phone. The others drop frames, starve the JS thread, or both: a UI thread at 117 fps next to a JS thread at 13 fps animates but does not respond.

<BenchChart group="stream|24|frame" metrics={['ui.fps', 'ui.dropped', 'js.fps']} />

**A list.** 200 rows in a `FlatList`, scrolled back and forth while ten values a second arrive in every row, rows mounting as they scroll in. Both Nitro paths keep the list at the panel's rate on the iPhones and lead on the Galaxy A22 (74–81 fps against plain text's 56, because a re-rendered `<Text>` is re-measured on every update). The digit-tree libraries fall to a few frames a second.

<BenchChart group="list|200|10" metrics={['ui.fps', 'ui.dropped', 'js.fps']} />

**Mounting 24.** This is where a native view pays for being native: 52–65 ms on the iPhones against 18–22 ms for plain text, about 1.5 ms of main-thread time per view, once. That is the order of the other native library and a quarter to a fifth of the Reanimated digit trees.

<BenchChart group="mount|24" metrics={['mountMs.p50']} />

**Memory.** 24 copies mounted and unmounted 40 times, the footprint read as a floor after a forced collection, growth per cycle. The Nitro number ends where it started on all three phones, within the few megabytes plain text moves by, and on the Galaxy A22 the live `View` count stays flat. The digit-tree libraries grow by 1–12 MB a cycle.

<BenchChart group="leak|24|40" metrics={['growthKbPerCycle']} />

## NitroInput

**Typing at eight keys a second.** The figure to read first is *rewritten keys*: a field that formats in JavaScript (`TextInput` with `onChangeText` → `Intl.NumberFormat` → `value`, and the libraries built on that pattern) shows the raw keystroke first and the formatted text a frame or two later, 10 keys in 12. NitroInput formats inside the native edit, plain or reflowing, and never rewrites a key; it costs 2–6 ms of JavaScript per key where the JS-formatted fields cost 40–50. The reflow adds its animation frames and about 20 ms of JavaScript per key, with nothing dropped.

<BenchChart group="type|8" metrics={['rewrites.keysWithRewrites', 'jsMsPerKey', 'settledMs.p95']} />

**Focus.** `focus()` to `onFocus`: 7–11 ms where `TextInput` takes 18–21 ms, because the call goes straight into the native view instead of through a Fabric view command and the batched event emitter.

<BenchChart group="focus" metrics={['ms.p50']} />

**Mounting 20 fields.** A Nitro view costs more to create than a `TextInput` on both platforms; unmounting costs about the same for every field.
